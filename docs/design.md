# 自适应深度学习 Agent 设计

- 状态：DRAFT，等待书面审阅
- 日期：2026-07-19
- 设计版本：1.0
- 适用仓库：`super-admin`
- 后续固化流程：`/opsx:propose` → `/writing-plans` → `/subagent-driven-development`

## 1. 背景与问题定义

现有系统已经能通过 Chrome 扩展采集网页，将正文转换为 Markdown，并提供任务管理、查看和编辑能力。但采集结束后，用户仍然主要是在阅读和收藏内容，没有形成可验证、可调用的理解。

本产品解决的不是单纯的“记不住”，而是阅读造成的熟悉感错觉：用户看过内容，觉得自己理解了，但无法脱离原文解释机制、识别适用边界，或把知识迁移到新的工作问题中。

产品承诺是：

> 帮助用户把文章和书籍转化为能够解释、判断和迁移应用的个人知识，而不是生成另一份摘要。

## 2. 目标用户与核心任务

第一版面向需要通过文章和书籍提升工作能力的知识工作者。系统不按职业角色硬编码学习流程，而是根据每份内容的学习目标自适应。

同一个用户阅读同一主题时可能有不同目标，例如：

- 理解一个机制并能向他人解释；
- 将方法用于新的工作情境；
- 判断一个观点何时成立、何时失效；
- 综合多个概念形成方案或决策。

职业角色只用于提供默认建议，不能替代用户对本次学习目标的确认。

## 3. 成功定义

“掌握”不等于记住原文细节，也不以聊天轮数、阅读时长或生成笔记数量衡量。

第一版的主要结果指标是迁移能力提升：用户在学习后，能够在未见过的新情境中正确调用原文的核心原理，并说明选择理由和适用边界。

系统使用四级理解状态：

1. `UNSEEN`：尚未获得用户理解证据；
2. `RECALLABLE`：能够复述主要结论；
3. `EXPLAINABLE`：能够用自己的话解释机制、因果关系和边界；
4. `TRANSFER_VALIDATED`：能够在新情境中正确迁移应用。

状态升级必须绑定用户原始回答、评价结果、来源证据和任务类型。系统不得用模型的主观印象直接生成百分制“掌握度”。

## 4. 产品原则

### 4.1 用户先生成，Agent 后帮助

学习发生在用户主动组织答案的过程中。Agent 应优先让用户预测、解释、比较或应用，再根据暴露的缺口提供提示和讲解。

### 4.2 路径动态，标准稳定

Agent 可以探索不同教学策略，但评价标准、权限边界、证据要求和停止条件必须稳定。

### 4.3 原文优先，扩展明确标注

所有与原文一致性的判断都必须给出来源锚点。模型补充知识必须标记为“原文外补充”，不得冒充作者观点，也不得用于判定用户答错。

### 4.4 覆盖完整，深度分层

系统应建立完整内容地图，但不平均训练所有细节。核心概念和与学习目标直接相关的内容需要达到解释或迁移层；次要事实可以保持可识别、可检索。用户可以提升某个概念的学习优先级。

### 4.5 用户拥有最终控制权

用户确认学习目标、内容切分、原子笔记和跨笔记链接。用户可以查看 Agent 的策略依据、覆盖建议、跳过当前步骤、重新评价或重置学习者画像。

## 5. 第一版范围

### 5.1 包含

- 完整多用户注册、登录和两级 RBAC；
- 现有 Chrome 扩展网页采集；
- EPUB 和包含可提取文本的 PDF 上传；
- 统一来源、章节、片段和稳定来源锚点；
- 概念地图与学习单元自动生成，由用户确认；
- 基于 LangGraph 的可暂停、可恢复教学 Agent；
- 受约束的教学策略探索和长期学习者画像；
- 诊断、自我解释、来源反馈、迁移任务和软掌握门槛；
- 用户回答形成原子笔记；
- 产品内笔记管理、少量跨来源链接建议和 Markdown 导出；
- 用户学习报告，以及平台级后台管理和运营诊断。

### 5.2 不包含

- 扫描 PDF、OCR 和复杂版面人工修复；
- 语音输入或实时语音 Tutor；
- 持续间隔重复和长期记忆提醒；
- 团队空间、教师看板或组织级课程管理；
- 公开分享、内容市场或协作编辑；
- 计费系统；
- 全库自动知识图谱；
- 通用全库问答和泛用 RAG；
- 多 Agent 协作架构；
- Agent 未经确认自动保存或修改用户笔记。

## 6. 核心用户流程

### 6.1 注册与进入产品

1. 用户使用邮箱和密码注册；
2. 完成邮箱验证后登录；
3. 首次进入时看到来源库和导入引导；
4. 用户可以在设置中生成仅允许网页采集的扩展 Token。

密码使用 Argon2id 哈希。邮件通过 `MailService` 抽象发送，开发环境写入本地诊断日志，生产环境使用 SMTP 配置。Web 登录使用短期访问令牌和可撤销、轮换的刷新令牌；刷新令牌只以哈希形式存储。

### 6.2 导入内容

网页继续由 Chrome 扩展采集。EPUB 和文本 PDF 由 Web 端上传到对象存储，并创建异步解析任务。

第一版单文件上限为 50 MB。服务端必须在写入对象存储前同时校验声明的 MIME、文件扩展名和文件签名，不能只信任浏览器传入的类型。

系统依次完成：

1. 格式和文件大小校验；
2. 文本提取与质量诊断；
3. 章节、段落和来源锚点生成；
4. 核心概念、依赖关系和建议学习单元生成；
5. 用户确认、拆分、合并或跳过学习单元。

扫描 PDF 必须返回明确的 `SCANNED_PDF_UNSUPPORTED`，不能以空内容或低质量内容继续建图。

### 6.3 建立学习契约

用户开始学习来源时需要确认：

- 学完后希望能够做什么；
- 本次可投入时间；
- 已有基础或已知概念；
- Agent 建议的学习单元和顺序。

Agent 可以推荐目标，但不能静默决定目标。

### 6.4 专注学习

默认界面一次只呈现一个思考任务。概念地图、原文和原子笔记通过侧边抽屉按需展开，避免同时争夺注意力。

每轮循环为：

1. Agent 观察目标、当前回答、概念状态、剩余时间和策略历史；
2. Agent 选择下一教学动作和策略；
3. 系统暂停，等待用户回答或确认；
4. 独立评价节点根据 Rubric 和来源锚点评价；
5. 系统持久化理解证据；
6. Agent 更新有证据支持的策略统计并选择下一步；
7. 达到迁移证据或用户主动结束时完成当前单元。

### 6.5 形成原子笔记

Agent 不直接把原文摘要保存成笔记。用户先用自己的话回答，Agent 再帮助拆分混合观点、补足上下文和明确边界。

保存前必须由用户确认。保存后，系统可以建议最多三个已有笔记链接，链接同样需要用户确认。

### 6.6 完成来源学习

用户完成整篇文章或整本书的目标单元后，需要：

- 重建整体概念结构；
- 完成一个跨单元综合迁移任务；
- 查看“已会、仍脆弱、有争议”的学习报告；
- 导出自己确认过的原子笔记。

## 7. 内容模型

### 7.1 统一学习来源

现有 `KnowledgeItem` 将迁移为通用 `LearningSource`。网页、EPUB 和 PDF 共享后续分析与学习流程。

核心结构为：

- `LearningSource`：用户拥有的逻辑来源；
- `SourceVersion`：一次具体采集或上传的不可变内容版本；
- `SourceSection`：章节或结构化分段；
- `SourceChunk`：可引用的最小内容片段；
- `SourceAnchor`：章节、页码或段落范围形成的稳定引用位置。

同一 URL 重新采集时创建新版本。已有学习会话继续固定到旧版本，用户明确选择后才能升级到新版本。

### 7.2 内容地图

每个来源版本生成：

- 概念列表；
- 概念重要级别；
- 概念之间的依赖和关联；
- 概念对应的来源锚点；
- 建议学习单元和顺序；
- 解析置信度和质量告警。

书籍和超长文章必须拆成可在约 20–40 分钟内完成的学习单元。切分由 Agent 提议、用户确认。

## 8. 教学 Agent 设计

### 8.1 为什么使用 LangGraph

学习过程包含多轮人机交互、条件分支、人工确认、跨请求恢复和策略调整。LangGraph 用于表达和持久化这个执行过程，避免在 Controller 或聊天记录中隐式维护状态。

LangChain 和 LangGraph 的使用边界为：

- `langchain`：模型适配、工具定义、结构化输出、重试和中间件；
- `@langchain/langgraph`：教学图、条件路由、Interrupt 和恢复；
- `@langchain/langgraph-checkpoint-postgres`：持久化 Graph Checkpoint；
- 不使用预制通用 ReAct Agent 代替领域图；
- 不引入向量数据库、多 Agent 模板或 Agent Server。

### 8.2 Graph State

`TutorGraphState` 至少包含：

- `sessionId`、`userId`、`projectId`；
- 当前来源版本和学习单元；
- 学习目标和剩余时间预算；
- 当前目标概念；
- 学习者策略快照；
- 待处理的教学动作；
- 最新用户回答和评价；
- 已写入的证据 ID；
- 当前轮次、最大轮次和终止原因；
- Graph 状态版本。

Graph State 只保存执行现场。用户、来源、概念、理解证据、原子笔记和学习者画像以 PostgreSQL 领域表为唯一真相。

### 8.3 Graph 节点

第一版采用一个主图，不使用多 Agent：

1. `load_context`：读取可信的用户、目标、内容和策略上下文；
2. `plan_action`：从允许的教学动作中选择下一步；
3. `build_action`：生成符合结构契约的用户可见动作；
4. `await_user`：使用 Interrupt 等待回答或确认；
5. `evaluate_answer`：按独立 Rubric 和来源证据评价；
6. `persist_evidence`：幂等写入理解证据；
7. `update_strategy_profile`：写入有证据支持的策略统计；
8. `route_next`：决定补学、迁移、笔记或完成；
9. `draft_atomic_note`：基于用户表达生成可编辑草稿；
10. `await_note_approval`：等待用户保存、修改或放弃；
11. `complete_unit`：生成单元结果并结束本次运行。

Interrupt 恢复可能重新执行节点，因此所有数据库写入使用确定性幂等键：`sessionId + turnId + operationType`。副作用放在用户恢复之后，或通过 upsert 保证重复执行不产生重复证据和笔记。

### 8.4 允许的教学动作

`TutorAction.kind` 固定为：

- `DIAGNOSE`：暴露已有理解；
- `SOURCE_REVIEW`：回到最相关原文；
- `SELF_EXPLAIN`：要求用户用自己的话解释；
- `ANALOGY`：建立类比并检查类比边界；
- `CONTRAST`：通过反例或对比案例澄清差异；
- `MICRO_EXPLAIN`：只解释已经确认的缺口；
- `TRANSFER`：在新情境中应用；
- `NOTE_DRAFT`：共同形成原子笔记；
- `REPLAN`：调整单元顺序或策略；
- `COMPLETE`：满足停止条件后结束。

模型不能自行创建新的动作类型。新增教学方法必须先进入代码和规格中的允许集合。

### 8.5 软门槛

未达到当前理解标准时，用户仍可继续，但相关概念保留为脆弱状态，并在综合迁移任务或学习报告中重新出现。只有符合评价证据时才能标记为 `TRANSFER_VALIDATED`。

## 9. 稳定输出与评价

规划、评价和笔记分别使用独立的 Prompt、Zod Schema 和版本号。

### 9.1 `TutorAction`

必须返回：

- 动作类型；
- 目标概念 ID；
- 使用的教学策略 ID；
- 用户可见内容；
- 来源锚点；
- 期望获得的理解证据；
- 选择该策略的机器可读理由；
- 难度和提示等级。

### 9.2 `EvaluationResult`

必须返回：

- `UNSUPPORTED`、`PARTIAL`、`SOUND` 或 `TRANSFER_VALIDATED`；
- 正确性、因果完整性、边界意识、来源一致性和迁移能力分项；
- 已确认的正确点；
- 遗漏和具体误解；
- 支持评价的来源锚点；
- 允许的下一步候选动作。

评价节点不得根据用户表达流畅程度直接判定理解，不得引用当前用户无权访问的内容。

### 9.3 结构失败

模型返回无法通过 Schema 的结果时：

1. 使用同一模型进行一次结构修复；
2. 修复失败后尝试配置的后备模型；
3. 仍失败则保存诊断并返回可恢复错误；
4. 不更新掌握状态或学习者画像。

## 10. 学习策略探索与用户画像

Agent 的价值在于探索更适合用户的学习方式，但不能用固定人格标签解释用户。

允许探索的策略包括：

- 问题优先或例子优先；
- 自我解释、类比、对比案例和反例；
- 提示阶梯速度；
- 问题粒度与难度；
- 原文暴露量；
- 中途形成笔记或单元结束后形成笔记。

第一版采用受约束探索策略：

- 新用户从平衡默认策略开始；
- 每个学习单元最多主动试验一种尚无充分数据的策略；
- 只在完成评价后更新策略统计；
- 主要观察迁移结果、提示次数、误解数量和笔记修改量；
- 个性化只改变路径与呈现，不降低掌握标准；
- 用户可以查看策略依据、禁用策略或重置全部统计。

学习者画像保存事实和证据，例如“对比案例在四次任务中减少了提示需求”，不保存“视觉型学习者”等未经验证的身份标签。

## 11. 原子笔记

原子笔记是学习过程的成果，也是用户个人知识库的基本单位。

每条 `AtomicNote` 包含：

- 一个单一、可独立判断的核心命题；
- 用户自己的解释；
- 用户提供或确认的个人例子；
- 适用条件和边界；
- 来源版本和锚点；
- 形成该笔记的理解证据；
- 用户确认时间；
- 至多三个经用户确认的关联笔记链接。

系统同时保留用户原始回答和确认后的笔记版本，以区分用户形成的理解与 Agent 的文字润色。

Markdown 导出必须使用稳定格式，包含标题、正文、来源、边界和双链。导出不包含模型内部评价、隐藏提示或其他用户数据。

## 12. 系统架构

### 12.1 后端边界

- `AuthModule`：注册、验证、登录、刷新、退出和密码重置；
- `SourceModule`：网页、EPUB、PDF、版本、章节和锚点；
- `LearningMapModule`：概念地图、学习单元和用户确认；
- `TutorModule`：LangGraph 编译、执行、Interrupt 和恢复；
- `EvaluationModule`：评价 Rubric 和理解证据；
- `NotesModule`：原子笔记、链接建议和导出；
- `LearnerProfileModule`：策略统计、解释、覆盖和重置；
- `ModelGatewayModule`：供应商、结构输出、重试、成本和调用记录；
- `AdminModule`：用户、任务、模型调用和配额诊断。

### 12.2 基础设施

- PostgreSQL 是唯一生产数据库；
- Redis 和 BullMQ 继续负责解析、内容建图、导出和清理任务；
- 原始 EPUB/PDF 存入对象存储；
- 开发环境使用本地存储适配器，生产使用 S3 兼容适配器；
- LangGraph Checkpoint 存入独立 PostgreSQL schema；
- 模型通过服务端统一配置的 OpenAI 兼容接口接入；
- 第一版不引入向量数据库，学习内容按已确认单元和来源锚点读取；
- 跨笔记候选先通过 PostgreSQL 全文检索缩小范围，再由模型重排。

### 12.3 后台任务和实时学习

以下任务进入 BullMQ：

- 文件解析；
- 内容质量检查；
- 概念地图生成；
- 大型 Markdown 导出；
- 来源和 Checkpoint 清理。

实时学习轮次不进入 BullMQ，避免用户交互被后台队列阻塞。模型调用完成并通过结构验证后，才更新领域状态。

## 13. 多用户认证与 RBAC

首版包含两种角色：

- `USER`：只能访问自己的来源、学习项目、会话、证据、画像和笔记；
- `ADMIN`：管理整个 Super Admin 平台，包括用户与角色、工具模块、任务、模型服务、配额与资源、系统诊断和审计。

`ADMIN` 是平台管理员，不是教师或“学习助手管理员”。管理员不能人工修改掌握度、指定下一道题或介入用户的学习决策。管理员默认只能查看元数据和脱敏诊断，不能直接查看用户正文、回答或笔记。需要内容级支持时必须使用显式、审计化的临时授权流程，该流程不在第一版 UI 中开放。

所有领域查询必须同时使用资源 ID 和可信认证上下文中的 `userId`。模型输入中的用户 ID、角色或权限声明一律不可信。

Chrome 扩展使用哈希存储的用户级 Token，Token 仅拥有 `capture:create` 作用域，不能读取学习数据或执行管理员操作。

## 14. 前端信息架构

### 14.1 一级菜单与权限边界

侧边栏新增两个职责不同的一级菜单：

- **学习助手**：普通用户和管理员均可见，是学习行为的入口，固定路由为 `/learning`；
- **后台管理**：仅 `ADMIN` 可见，是整个 Super Admin 平台的管理入口，固定路由为 `/admin`。

不设置“学习助手管理”一级菜单。学习助手的系统级配置属于后台“工具管理”中的一个模块，不能与用户学习工作区并列成独立管理后台。管理员登录后同时看到“学习助手”和“后台管理”；普通用户看不到后台菜单，直接访问 `/admin/*` 时服务端必须返回 403，不能只依赖前端隐藏。

现有“知识采集”继续负责网页采集任务与诊断，不作为学习入口。“学习助手”读取采集成功的文章，并提供 EPUB/PDF 上传。

### 14.2 学习助手

学习助手使用面向学习任务的产品布局：

- 来源库；
- 来源详情与内容地图；
- 专注学习；
- 学习报告；
- 原子笔记库；
- 学习者设置；
- 账户与扩展 Token 设置。

专注学习页默认只显示当前问题、回答区、反馈和主要动作。以下内容按需展开：

- 左侧抽屉：概念地图和单元进度；
- 右侧抽屉：原文证据和原子笔记草稿；
- 顶部：学习目标、当前单元、时间预算和退出；
- 底部：本轮形成的证据和仍脆弱概念。

学习助手路由包括：

- `/learning`：学习首页与来源库；
- `/learning/sources/:id`：来源详情、解析状态和内容地图；
- `/learning/projects/:id`：学习目标、学习单元和整体进度；
- `/learning/sessions/:id`：专注学习会话；
- `/learning/reports/:id`：来源完成报告、脆弱概念和综合迁移证据；
- `/learning/notes`：原子笔记库；
- `/learning/profile`：学习策略画像和用户控制。

### 14.3 后台管理

后台管理沿用现有高密度控制台风格，覆盖整个平台，而不是只覆盖学习助手：

- `/admin`：平台运行概览与关键告警；
- `/admin/users`：用户、角色和账号状态；
- `/admin/users/:id`：用户详情、会话撤销、角色与配额覆盖；
- `/admin/tools`：工具注册、启停、版本和模块配置；
- `/admin/tools/learning-assistant`：学习助手的模型、Prompt、文件限制和策略开关；
- `/admin/models`：模型供应商、模型配置、调用统计、失败和成本；
- `/admin/quotas`：用户级和全局资源配额；
- `/admin/jobs`：所有工具的后台任务、重试和异常；
- `/admin/audit`：管理员操作和安全审计记录。

后台只展示平台级指标、配置、任务元数据和脱敏诊断。用户正文、回答、原子笔记和 LangGraph State 不在后台页面中展示。

### 14.4 页面与状态覆盖

进入 OpenSpec 前，设计原型必须覆盖以下完整闭环，不能只提供首页和概念图：

| 领域 | 页面或容器 | 必须覆盖的关键状态 |
|---|---|---|
| 认证 | 登录、注册、邮箱验证、找回与重置密码 | 默认、提交中、验证成功、Token 失效、字段错误 |
| 来源 | 学习首页、导入弹窗、来源详情 | 空库、上传中、解析中、解析失败、扫描 PDF 拒绝、可学习 |
| 学习契约 | 目标、时间、已有基础、学习单元确认 | Agent 建议、用户拆分/合并/跳过、未确认不可开始 |
| 专注学习 | 问题、回答、评价、追问、提示、原文抽屉 | 等待回答、生成中、结构失败、可恢复、主动结束 |
| 笔记 | 原子笔记草稿、笔记库、笔记详情 | 待确认、编辑、链接建议、无笔记、导出 |
| 完成 | 来源学习报告 | 已会、仍脆弱、有争议、综合迁移任务通过/未通过 |
| 画像 | 学习者画像与策略控制 | 查看依据、禁用策略、重置、无足够证据 |
| 后台用户 | 用户列表、用户详情抽屉 | 搜索筛选、禁用/恢复、角色变更、最后管理员保护、撤销会话 |
| 后台工具 | 工具列表、模块配置 | 注册状态、启停、版本、学习助手配置、配置校验失败 |
| 后台模型 | 模型供应商与模型配置 | 密钥遮罩、连接测试、超时、后备模型、Prompt 版本 |
| 后台资源 | 默认配额和用户覆盖 | Token、存储、文件、并发限制以及越界提示 |
| 后台任务 | 跨工具任务中心 | pending、running、success、failed、retry、stalled |
| 后台审计 | 审计日志 | 操作者、目标、原因、结果、时间和筛选导出 |

导入、用户详情和笔记详情优先使用可深链的弹窗或抽屉；其余领域使用独立页面。状态属于页面验收的一部分，不能通过额外的静态说明代替。

## 15. API 边界

公开 API 按领域分组：

- `/api/auth/*`：注册、验证、登录、刷新、退出、找回和重置密码；
- `/api/sources/*`：来源列表、上传、解析状态、版本和删除；
- `/api/learning-projects/*`：学习目标、内容地图、单元确认和进度；
- `/api/learning-sessions/*`：创建会话、读取状态、提交回答、恢复 Interrupt 和结束；
- `/api/atomic-notes/*`：草稿确认、编辑、链接和导出；
- `/api/learner-profile/*`：读取依据、禁用策略和重置；
- `/api/admin/*`：用户与角色、工具管理、任务、模型服务、配额、系统诊断和审计。

现有 `/api/tools/knowledge-capture/capture` 保留供扩展调用，但必须使用用户级作用域 Token，并写入该用户的 `LearningSource`。

提交回答和恢复 Interrupt 使用客户端幂等键。服务端通过基于 `fetch` 的 SSE 数据流发送运行节点、用户可见增量文本和最终结构结果；只有最终结构结果通过 Schema 验证并成功写入领域数据后，客户端才更新掌握状态。

## 16. 数据迁移

SQLite 迁移到 PostgreSQL 时：

1. 根据部署环境创建初始管理员用户；
2. 将现有 `KnowledgeItem` 转换为管理员拥有的 `LearningSource` 和首个 `SourceVersion`；
3. 将现有 Job 保留并关联管理员；
4. 给现有 `ApiToken` 增加所有者和 `capture:create` 作用域，使原扩展 Token 继续有效；
5. 对内容生成稳定锚点，但不自动创建学习项目；
6. 完成数量、内容哈希和关联完整性校验后，才切换生产连接；
7. 保留只读 SQLite 备份用于回滚，不支持两个数据库同时写入。

## 17. 错误处理与恢复

### 17.1 内容解析

- 不支持的格式：拒绝并显示允许格式；
- 扫描 PDF：返回明确分类和处理建议；
- 章节结构缺失：生成线性单元并标记低置信度；
- 内容过大：异步分批处理，不截断后假装完成；
- 重复上传：按用户和内容哈希提示复用或创建新版本。

### 17.2 Agent 执行

- 模型超时：保存当前 Checkpoint，允许原位置重试；
- 结构输出失败：修复一次、后备模型一次，失败后不改变掌握状态；
- 浏览器断开：Graph 保持 Interrupt，重新进入后恢复；
- 重复提交：按会话、轮次和客户端幂等键去重；
- 来源版本已删除：停止会话并说明引用不可用；
- 达到轮次或成本上限：生成诚实的未完成报告，不伪造完成状态。

### 17.3 删除

删除来源时提供两种明确选择：

- 删除来源及所有派生学习数据；
- 删除来源但保留用户确认的原子笔记，笔记标记来源已删除。

对象存储删除和 LangGraph Checkpoint 清理由幂等后台任务完成。

## 18. 安全与隐私

- 上传内容、网页正文和用户回答全部视为不可信输入；
- 原文中的指令不得改变系统提示、工具权限或评价规则；
- 模型工具只接受服务端注入的可信 `userId`，不接受模型生成的身份参数；
- 日志不得记录密码、刷新令牌、扩展 Token、Cookie、完整正文或完整用户回答；
- 对象存储路径必须包含不可猜测标识，并通过服务端鉴权访问；
- 用户删除账号时，异步清理来源、文件、Checkpoint、学习数据和笔记；
- 管理员操作、Token 创建和删除操作必须保留审计记录。

## 19. 可观察性与成本控制

每次模型调用记录：

- 用户、会话和用途；
- 供应商、模型和 Prompt 版本；
- 输入输出 Token、耗时和估算成本；
- 结构验证、重试和后备模型结果；
- 关联 Graph 节点；
- 脱敏后的错误分类。

管理员可以按用户、模型、用途和日期查看调用量与失败率。达到用户级配额时，系统在发起模型调用前拒绝，并保留可恢复会话状态。

## 20. 验收标准

### 20.1 功能验收

- 用户能够注册、验证邮箱、登录、刷新会话、退出和重置密码；
- 普通用户和管理员权限符合两级 RBAC；
- 普通用户和管理员均能看到一级菜单“学习助手”，并从 `/learning` 进入学习功能；
- 只有管理员能看到一级菜单“后台管理”并访问 `/admin/*`；
- 系统中不存在独立一级菜单“学习助手管理”，学习助手配置位于后台“工具管理”中；
- 普通用户直接访问 `/admin/*` 时必须收到 403，不能只依赖前端隐藏菜单；
- “学习助手”中不出现模型、Prompt、任务运维、平台配额或用户管理入口；
- “后台管理”覆盖整个平台，且不展示用户正文、回答、原子笔记或 LangGraph State；
- 管理员能够搜索和筛选用户、禁用或恢复账号、撤销全部登录会话并调整角色；
- 系统必须阻止管理员禁用或降级平台中的最后一个有效管理员；
- 角色、账号状态、配额和模型配置变更必须填写原因并生成审计事件；
- 模型密钥在读取接口和管理界面中始终遮罩，管理员能够执行独立的连接测试；
- 工具管理能够显示 ToolManifest 注册状态，并将学习助手配置作为工具模块配置而非独立后台；
- 任务中心能够按工具和状态筛选任务，只有满足幂等约束的失败任务可以重试；
- 任意两个用户不能通过修改 ID 读取或修改对方资源；
- Chrome 扩展采集的文章归属于对应 Token 用户；
- 用户能够上传 EPUB 和文本 PDF，并看到解析进度、地图和质量告警；
- 扫描 PDF 被明确拒绝且不会进入内容建图；
- Agent 提议的学习单元只有经用户确认后才能开始；
- 学习会话可在关闭页面后从原 Interrupt 恢复；
- Interrupt 恢复、网络重试和重复提交不会产生重复证据或笔记；
- 只有迁移任务通过时才能产生 `TRANSFER_VALIDATED`；
- 用户能够查看并重置教学策略画像；
- 原子笔记必须经用户确认才能保存或建立链接；
- Markdown 导出只包含当前用户确认的笔记；
- 来源删除和账号删除能清理对应数据库记录、对象和 Checkpoint。

### 20.2 AI 质量验收

- 所有原文一致性评价都引用当前来源版本中存在的有效锚点；
- 黄金数据集中至少 95% 的引用被人工判断为能支持对应评价；
- 使用至少 30 组人工标注回答校准评价器，`通过/不通过` 与人工判断的一致率不低于 85%；
- Prompt Injection 测试内容不能改变 Agent 的工具、权限、输出 Schema 或评分标准；
- 结构输出经过修复和后备模型后仍失败时，不得更新任何掌握状态；
- 学习者画像中的每条策略结论都能追溯到具体完成任务和指标，不出现固定人格标签。

### 20.3 学习效果验收

- 每个试点来源至少包含一组同能力、不同情境的前测和后测迁移任务；
- 首轮真实试点包含至少 3 位目标用户，每人完成一篇真实工作相关文章；
- 试点用户的后测迁移表现中位数至少提升一个 Rubric 等级；
- 用户能够指出最终笔记中哪些内容来自自己的理解，哪些经过 Agent 润色；
- 若试点没有达到迁移提升，停止扩大功能范围，优先修正教学策略和评价器。

### 20.4 工程验收

- 后端单元测试、集成测试和 E2E 测试通过；
- 前端类型检查和生产构建通过；
- PostgreSQL 数据迁移在生产数据副本上完成数量、哈希和关联校验；
- LangGraph Checkpoint 与领域数据不存在双向覆盖或重复写入；
- 模型超时、进程重启和浏览器断开场景均能恢复；
- 所有新增 API 有鉴权、所有权校验、输入验证和错误分类测试。

## 21. 方案对比与最终决策

### 21.1 纯对话教练

优点是实现快、交互自然。缺点是覆盖、掌握和进度难以验证，容易成为会说话的摘要器。拒绝作为产品架构，只保留自然对话的表面体验。

### 21.2 固定学习状态机

优点是稳定、容易测试。缺点是无法探索不同用户需要的教学策略。保留稳定动作、证据和权限规则，但不固定每轮路径。

### 21.3 受约束的 LangGraph 教学 Agent

路径由 Agent 动态选择，输出、评价、权限和停止条件由系统固定。该方案同时满足稳定输出、人工确认、跨请求恢复和教学策略探索，因此被选为最终方案。

### 21.4 多 Agent 协作

规划、教学、评价和笔记可以拆成多个 Agent，但会增加延迟、成本、状态冲突和调试复杂度。第一版使用单一 Graph 内的职责隔离节点；只有评测证明单图无法满足隔离需求时才重新评估。

## 22. 发布顺序

1. 使用人工方式为 3 位目标用户执行一次完整学习流程，校准动作集合和 Rubric；
2. 完成 PostgreSQL、多用户认证、RBAC 和所有权迁移；
3. 完成统一来源、对象存储和 EPUB/PDF 管道；
4. 完成 LangGraph 教学运行时和理解证据；
5. 完成专注学习界面和原子笔记；
6. 完成学习者画像、管理员诊断和黄金数据集；
7. 在受控用户中验证迁移提升和系统稳定性；
8. 达到验收标准后开放注册。

本设计经书面批准后，使用一个 OpenSpec change：`add-adaptive-learning-assistant`。

OpenSpec 必须产生：

- `proposal.md`：问题、动机、变更和影响；
- `design.md`：引用本文件并固化工程决策；
- `specs/user-access/spec.md`；
- `specs/learning-sources/spec.md`；
- `specs/adaptive-tutoring/spec.md`；
- `specs/learner-profile/spec.md`；
- `specs/atomic-notes/spec.md`；
- `specs/platform-administration/spec.md`；

OpenSpec requirements 必须使用可验证场景覆盖正常路径、权限、失败和恢复。所有 artifact 通过严格校验并经用户批准后，才允许进入 `/writing-plans`。

## 24. 工作流门禁

本功能严格使用以下顺序：

1. `/brainstorming`：生成并批准本设计；
2. `/web-design-engineer`：生成并批准前端设计原型；
3. `/opsx:propose`：生成 proposal、delta specs、OpenSpec design 和 tasks；
4. `/writing-plans`：把已批准 tasks 拆成每项 2–5 分钟的 TDD 实施步骤；
5. `/subagent-driven-development`：逐任务实现并进行双阶段复核；
6. `/requesting-code-review`：对完整变更进行代码审查；
7. `/opsx:archive`：验证实现后归档规格和变更记录。

任何阶段未获批准或未通过验证，不得跳到下一阶段。
