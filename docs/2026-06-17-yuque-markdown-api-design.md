## Problem Statement

语雀文档采集回来后，后台 Markdown 编辑器显示格式混乱。根本原因：语雀使用自研 Lake Editor，文档数据分两层存储——**湖格式 XML（body_lake）**和**自定义元素渲染层（ne-* HTML）**。当前方案抓取的是渲染层 HTML，然后通过 Readability + Turndown 转换为 Markdown，存在三个致命问题：

1. **Turndown 不认识 `<ne-*>` 自定义元素**——标题、列表、加粗等格式全部丢失
2. **代码块、图片、分割线等卡片内容在静态 DOM 中为空**——`<ne-card data-card-name="codeblock">` 的内容由 JS 动态加载，`outerHTML` 抓不到
3. **语雀 DOM 节点密度是普通文章的 7 倍**（1.4 万节点 vs 2000），噪音极大

## 核心洞察

**语雀 Web 前端本身就会调用内部 API 获取文档数据，且该 API 支持直接返回 Markdown。** 参考开源项目 [yuque-dl](https://github.com/gxr404/yuque-dl) 的实现：

```
GET {host}/api/docs/{articleSlug}?book_id={bookId}&merge_dynamic_data=false&mode=markdown
Cookie: _yuque_session={token}
→ response.data.sourcecode  // 就是干净的 Markdown！
```

**这意味着：对于语雀文档，我们根本不需要解析 HTML、不需要 Readability、不需要 Turndown。直接调 API 拿 Markdown 即可。**

## What Makes This Cool

- 代码块、图片、表格、公式 **零丢失**——API 返回的 Markdown 是语雀服务端转换的，保真度 100%
- **分层策略**：语雀走 API 直采，其他网站走原有 HTML→Markdown 管线，互不干扰
- 实现量很小——扩展加几行，后端加一个 fetch，不需要引入任何新依赖

## Constraints

- 语雀 API 需要 `_yuque_session` cookie（扩展已在发送）
- 语雀 API 需要 `bookId`（数字 ID，不在 URL 中，需从 `window.appData` 提取）
- `window.appData` 在页面加载后即可用（SSR 嵌入），不需等待 JS 渲染
- 非语雀 URL 保持现有管线不变
- 企业版语雀 (`*.yuque.com` 自有域名) cookie key 可能不是 `_yuque_session`，需兼容

## Premises

1. **语雀 API 返回的 Markdown 质量优于我们自行转换** — 同意（语雀服务端从 lake XML 转 Markdown，100% 保真）
2. **分层策略优于统一方案** — 同意（语雀专用 API 路径 + 通用 HTML 路径，各走各的）
3. **API 调用应在后端而非扩展中完成** — 同意（后端可做错误处理、重试、日志；扩展只负责数据采集）
4. **API 失败时以现有 HTML 管线为 fallback** — 同意（不影响可用性）
5. **不需要新增数据库字段** — 同意（`contentMarkdown` 存 Markdown，`contentHtml` 存 API 返回的 HTML 版本，`source` 标记为 `"yuque"`）

## Approaches Considered

### Approach A: 扩展直接调语雀 API（已评估，未选中）

```
扩展: executeScript 提取 window.appData → 调语雀 API 拿 Markdown → 发给后端
后端: 直接存储 Markdown，不做转换
```

- 优点：扩展已有 cookie，调 API 最直接
- 缺点：扩展逻辑变重；API 失败时需传 pageHtml 做 fallback，payload 更大
- 结论：放弃——扩展职责应保持简单（数据采集），API 调用逻辑放在后端更灵活

### Approach B: 后端调语雀 API（推荐）✅ 选中

```
扩展: executeScript 提取 window.appData（bookId + slug + host），
     连同 cookies + pageHtml（作为 fallback）一起发给后端
后端: 检测 URL 是语雀 → 用 cookies 调语雀 API 拿 Markdown
     非语雀 → 走现有 Readability + Turndown 管线
     API 失败 → fallback 到现有管线
```

- 优点：扩展改动最小；后端可做统一错误处理、日志、重试；fallback 逻辑清晰
- 缺点：cookie 需传给后端（已在传，无新增风险）
- 结论：选中

### Approach C: 从 `window.appData` 提取 lake XML 自行转换

```
扩展: 提取 window.appData.doc.body_lake (lake XML)
后端: 解析 lake XML → 逐元素转 Markdown（参考 Yuque2Markdown 的12种 card 转换规则）
```

- 优点：不依赖语雀 API 的稳定性
- 缺点：需实现完整的 lake XML 解析器（12 种 card 类型、嵌套结构、属性处理）；维护成本高；语雀 API 本身就是从 lake XML 转的，重复造轮子
- 结论：放弃——除非语雀 API 不可用，否则不值得

## Recommended Approach

**方案 B：后端调语雀 API，分层策略**

### 扩展改动细节

**改动涉及 3 个函数，因为 `pageAppData` 需要贯穿整条采集链：**

```
readDirectlyFromTab   → 注入 executeScript，提取 window.appData
readFromContentScript → 同样需要提取（否则 content-script 成功时 appData 丢失）
readTabState          → 合并两条路径的 pageAppData
handleCapture         → 将 pageAppData 附到 POST payload
```

**① `readDirectlyFromTab` — 注入脚本中提取 `window.appData`：**

```javascript
// service-worker.js: readDirectlyFromTab 中 executeScript 的 func 内增加
func: () => {
  // ... 现有 localStorage + pageHtml 逻辑 ...

  // 新增：提取语雀 appData
  let pageAppData = null;
  try {
    if (window.appData && window.appData.doc) {
      pageAppData = {
        bookId: window.appData.doc.book_id,
        articleSlug: window.appData.doc.slug,
        host: window.location.host,
      };
    }
  } catch (e) {
    // appData 不存在或结构不同，忽略
  }

  return {
    localStorage: localStorageData,
    pageTitle: document.title || '',
    pageHtml: document.documentElement ? document.documentElement.outerHTML : '',
    pageAppData,  // 新增
  };
},
```

**② `readFromContentScript` — 同样增加 `pageAppData` 提取：**

如果页面已注入 `content-script.js`，当前逻辑优先走 content-script 路径（代码更轻量）。该路径也需要能提取 `pageAppData`。改动方式：在 `content-script.js` 的 `getPageSnapshot` 响应中增加 `pageAppData` 字段，或者 `readTabState` 中无论走哪条路径，统一再调一次轻量的 executeScript 单独提取 `window.appData`。

**建议采用后者**——在 `readTabState` 中，无论 content-script 是否成功，始终额外调一次 executeScript 提取 `pageAppData`（~5ms 开销，可忽略）：

```javascript
async function readTabState(tabId) {
  const fromContentScript = await readFromContentScript(tabId);
  let result;
  if (fromContentScript.pageHtml) {
    result = fromContentScript;
  } else {
    const fromDirectRead = await readDirectlyFromTab(tabId);
    result = {
      localStorage: Object.keys(fromContentScript.localStorage).length > 0
        ? fromContentScript.localStorage
        : fromDirectRead.localStorage,
      pageHtml: fromDirectRead.pageHtml,
      pageTitle: fromDirectRead.pageTitle || fromContentScript.pageTitle || '',
    };
  }

  // 新增：轻量提取 pageAppData（无论走哪条路径都执行）
  try {
    const [appDataInjection] = await chrome.scripting.executeScript({
      target: { tabId },
      func: () => {
        try {
          const ad = window.appData;
          if (ad && ad.doc) {
            return { bookId: ad.doc.book_id, articleSlug: ad.doc.slug, host: location.host };
          }
        } catch (e) { /* ignore */ }
        return null;
      },
    });
    result.pageAppData = appDataInjection?.result || null;
  } catch (e) {
    result.pageAppData = null;
  }

  return result;
}
```

**③ `handleCapture` — 将 `pageAppData` 附到 POST payload：**

```javascript
// handleCapture 中，payload 构建处增加一行：
const payload = {
```

### 后端改动细节

```typescript
// capture.processor.ts 新增函数

const YUQUE_HOST_PATTERN = /yuque\.com$/i;

function isYuqueUrl(url: string): boolean {
  try {
    const host = new URL(url).host;
    return YUQUE_HOST_PATTERN.test(host) || host.endsWith('.yuque.com');
  } catch {
    return false;
  }
}

interface YuquePageAppData {
  bookId: number;
  articleSlug: string;
  host: string;
}

async function fetchYuqueMarkdown(
  appData: YuquePageAppData,
  cookies: any[],
): Promise<{ markdown: string; html: string; title: string }> {
  const cookieHeader = cookies
    .map((c) => `${c.name}=${c.value}`)
    .join('; ');

  const baseUrl = `https://${appData.host}/api/docs/${appData.articleSlug}`;
  const params = `book_id=${appData.bookId}&merge_dynamic_data=false`;

  // 1. 获取 Markdown
  const mdRes = await fetch(`${baseUrl}?${params}&mode=markdown`, {
    headers: { cookie: cookieHeader },
  });
  if (mdRes.status === 401 || mdRes.status === 403) {
    throw Object.assign(
      new Error('Yuque API authentication failed — cookie may be expired'),
      { jobErrorType: 'LOCKED_CONTENT' },
    );
  }
  const mdJson = await mdRes.json();
  const markdown = mdJson?.data?.sourcecode || '';

  // 2. 获取 HTML（备用，存入 contentHtml）
  const htmlRes = await fetch(`${baseUrl}?${params}`, {
    headers: { cookie: cookieHeader },
  });
  const htmlJson = await htmlRes.json();
  const html = htmlJson?.data?.content || '';

  return {
    markdown,
    html,
    title: mdJson?.data?.title || '',
  };
}
```

```typescript
// capture.processor.ts 第 289 行附近
export async function captureProcessor(job: Job) {
  // 变更：destructure 增加 pageAppData 和 cookies
  const { url, jobRecordId, pageHtml, pageAppData: rawPageAppData, cookies } = job.data;
  const pageHtmlMeta = parsePageHtmlMeta(job.data.pageHtmlMeta);

  // 解析 pageAppData
  const pageAppData: YuquePageAppData | null =
    typeof rawPageAppData === 'string'
      ? (() => { try { return JSON.parse(rawPageAppData); } catch { return null; } })()
      : rawPageAppData || null;

  // ... pageHtml 为空检查（不变）...
  // ... documentDom / content 提取（用于 fallback 和 title 解析）...

  // ── 语雀 API 路径 ──
  if (isYuqueUrl(url) && pageAppData?.bookId && Array.isArray(cookies)) {
    try {
      const yuqueResult = await fetchYuqueMarkdown(pageAppData, cookies);
      if (yuqueResult.markdown && yuqueResult.markdown.trim().length >= 100) {
        // 成功！直接用 API 返回的数据
        const title = yuqueResult.title || resolveTitle(documentDom.window.document, content, pageHtmlMeta, url);
        const item = await prisma.knowledgeItem.create({
          data: {
            title,
            url,
            source: 'yuque',
            contentHtml: yuqueResult.html || content?.content || '',
            contentMarkdown: yuqueResult.markdown,
            status: 'published',
            jobId: jobRecordId,
          },
        });
        return { itemId: item.id };
      }
    } catch (err: any) {
      // API 失败时静默 fallback 到 HTML 管线（LOCKED_CONTENT 除外）
      if (err.jobErrorType === 'LOCKED_CONTENT') throw err;
      console.warn(`[capture] Yuque API failed for ${url}, falling back to HTML pipeline:`, err.message);
    }
  }

  // ── 通用 HTML 管线（非语雀 + 语雀 fallback）──
  // ... 现有逻辑不变 ...
  const markdown = turndown.turndown(content.content);
  const title = resolveTitle(...);
  const item = await prisma.knowledgeItem.create({
    data: {
      title,
      url,
      contentHtml: content.content,
      contentMarkdown: markdown,
      status: 'published',
      jobId: jobRecordId,
    },
  });
  return { itemId: item.id };
}
```

### 错误处理矩阵

| 场景 | 行为 | Job 状态 |
|------|------|---------|
| URL 是语雀 + `pageAppData` 完整 + API 成功 | 使用 API 返回的 Markdown | `success` |
| URL 是语雀 + `pageAppData` 缺失 | 静默 fallback 到 HTML 管线 | 按 HTML 管线结果 |
| URL 是语雀 + API 返回空/网络错误 | 静默 fallback 到 HTML 管线 | 按 HTML 管线结果 |
| URL 是语雀 + API 返回 401/403（cookie 过期） | 抛出 `LOCKED_CONTENT` 错误，**不 fallback** | `failed`（提示用户重新登录语雀后重采） |
| URL 非语雀 | 直接走 HTML 管线 | 按 HTML 管线结果 |

`LOCKED_CONTENT` 在 API 401 时不 fallback 的原因：cookie 已过期意味着 HTML 管线同样拿不到完整内容（付费/登录墙），fallback 无意义。让任务标记为 failed 并给出明确提示，比存入残缺内容更好。

### 语雀 API 响应结构

```json
{
  "data": {
    "id": 123456,
    "title": "文档标题",
    "slug": "doc-slug",
    "type": "doc",
    "format": "lake",
    "sourcecode": "# 标题\n\n这是 **Markdown** 正文\n\n```js\ncode block\n```",
    "content": "<div data-df=\"lake\">...</div>",
    "created_at": "2025-01-01T00:00:00Z",
    "content_updated_at": "2025-06-01T00:00:00Z"
  }
}
```

`sourcecode` 字段就是语雀服务端从 lake XML 转换好的 Markdown。
`content` 字段是 HTML 版本，存入 `contentHtml` 备用。

- [ ] 语雀文档采集后，Markdown 编辑器显示格式完整（标题、加粗、列表、行内代码）

- [ ] 语雀图片链接正确出现在 Markdown 中
- [ ] 非语雀 URL 采集行为不变（回归测试）
